# Feature map

One file per feature. `covers:` lists the source globs it owns, `docs:` the pages a verdict judges, and `journeys/<feature>.mjs` its journeys. `dms-control map` checks that every user-facing file is covered and that every feature has its journeys and existing docs pages.

The skill serves this checkout as the dashboard of the dms playground (`dms-control up --renderer`), so a feature is reached through the dashboard, the frontend server's HTTP surface or the `ajs dms` CLI.

| Feature | What the user does | Journeys |
|---|---|---|
| [build](build.md) | The production path of the CLI: `build` into a workspace, `start` serving it against a backend, and `dev` serving the project with a backend on the same machine. |  |
| [cli](cli.md) | The `ajs dms` command line as a user meets it: its help and version, the options every command accepts, the exit codes and the framed output, the `.env` files and the environment variables, and the update notice. |  |
| [emails](emails.md) | The frontend server renders the DMS's e-mail templates when the backend asks: complete HTML with no Vue hydration comments, links built on the dashboard's origin, and a route that only accepts the backend's signed render requests. | a-rendered-email-carries-no-hydration-markers-and-links-to-the-dashboard, the-render-route-takes-one-signed-single-use-token-per-render |
| [icons](icons.md) | The browser never asks a third party for an icon. The frontend server serves collections at `/api/_dms/icons/<prefix>.json`, draws icons on the server and sends each once per page in a hidden sprite. | the-icon-route-answers-iconify-json-from-the-installed-collections, the-icon-route-refuses-unknown-collections-and-bad-names, one-sprite-draws-each-icon-once-and-no-third-party-is-asked, a-signed-out-page-loads-the-icon-bundle-only-when-the-visitor-acts |
| [modules](modules.md) | A frontend module is a package that registers pages, components, plugins, server routes and an app config. The loader reads each module in place and writes its public options into every page by module id. | the-modules-public-options-reach-every-page-and-no-secret-does |
| [proxy](proxy.md) | The frontend server sends the paths that a backend prefix covers to the backend: it adds the session's token on the server, refuses a state-changing request without the frontend's own `Origin`, relays a documented set of headers, never follows a redirect, compresses eligible answers, streams bodies both ways and caps a body when a prefix says so. A public endpoint is the one exception to the Origin rule. |  |
| [rendering](rendering.md) | How the frontend server answers a page: a document request is rendered on the server and carries the Inertia page object, the data payload and private caching headers; an `X-Inertia` visit answers the page object as JSON; the site layout travels once per account and workspace for five minutes; partial reloads pick props; a stale asset version answers 409; an unknown path renders the error page with its status; key hints are drawn for the keyboard platform of the request. | a-first-load-is-rendered-on-the-server, an-inertia-visit-answers-a-json-page-object, a-stale-asset-version-answers-409-with-the-location, the-site-layout-travels-once-per-account-and-workspace, following-a-link-is-an-inertia-visit-without-the-layout, partial-reloads-send-only-the-props-they-name, the-data-a-page-read-is-drawn-by-the-server-and-handed-over, an-unknown-page-renders-the-error-page-with-its-status, key-hints-are-drawn-for-the-keyboard-the-server-was-told, the-payload-is-escaped-so-data-cannot-close-its-script, choosing-a-tab-changes-only-the-query-in-the-browser |
| [routing](routing.md) | One owner answers each path: the renderer's files, then the modules' `dms.server.ts` routes, then the backend proxies, then the pages. A module route owns its path for every method, takes parameters, a body limit, the Origin rule and `no-store` by default, and warns about every declaration it settles silently. Route rules set a page's caching, server rendering and headers. |  |
| [sessions](sessions.md) | The session is a sealed, `HttpOnly`, `SameSite=Lax` cookie, scoped to the backend, that holds the tokens on the server. The module that owns sign-in registers hooks that renew a refused session once and retry the visit, build the `user` and `session` page props and send a signed-out visit to sign-in. `POST /auth/establish` opens a session from a declared backend endpoint. |  |
| [smoke](smoke.md) | The fixed journey every verdict runs, whatever the diff touches: the renderer serves the dashboard of a fresh platform, the administrator signs in through the rendered form and stays signed in across a reload. | smoke |
| [static-files](static-files.md) | `ajs dms start` serves the files `ajs dms build` made: pre-compressed copies, MIME types, cache headers and conditional requests, none of the dot files. It reports what it serves to the backend, writes nothing into a read-only workspace, stops on a signal and refuses to run without a build or a session secret. `ajs dms dev` serves the sources, hides the generated secrets and the modules' server code, and answers a Vite error with 500. |  |
| [verify-source](verify-source.md) | `ajs dms verify-source`: builds and type-checks unpublished frontend modules on top of the DMS core layer of the `@antelopejs/dms` the project installs, in a temporary workspace, with no backend. |  |
| [workspace](workspace.md) | The generated workspaces under `~/.antelopejs/dms-frontend`: how `prepare` writes them, how `workspaces` lists them, how `clean` removes them, and how the manifest cache stands in for a backend that is out of reach. |  |
