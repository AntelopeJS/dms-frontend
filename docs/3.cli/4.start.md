# start

`ajs dms start` serves the production frontend `ajs dms build` made from the project, in `<project>/.dms-frontend` or the one in `--workspace`. It computes the modules' public options again from the project's configuration and the variables it runs with, reads the secrets of its environment, and fetches nothing before the server is ready.

```text
$ ajs dms start --help
Usage: ajs dms start [options]

Serve the production frontend ajs dms build made from the project. The modules'
public options are computed again from the project's configuration and the
current environment variables, so a deployment's variables need no rebuild.
Reads DMS_SESSION_SECRET and the server's secrets (DMS_HTML_RENDER_SECRET,
DMS_OAUTH_RELAY_SECRET) from its environment, and tells the backend once ready
which module versions it serves.

Options:
  -b, --backend-url <url>  Backend URL to serve; required (env:
                           DMS_API_BASE_URL)
  -p, --port <port>        Port to serve on (default: "3001", env: PORT)
  --project <dir>          The AntelopeJS project whose antelope.config.ts and
                           installed modules make the frontend (default: ".")
  -e, --env <environment>  The AntelopeJS environment whose configuration
                           applies, as ajs project start -e (default:
                           "production", env: ANTELOPEJS_LAUNCH_ENV)
  --workspace <dir>        Serve the build in this directory instead of
                           <project>/.dms-frontend; start writes nothing into it
                           (env: DMS_WORKSPACE_DIR)
  -h, --help               Show help for a command
```

## The modules' public options

`start` evaluates `antelope.config.ts` again, with the variables of its own environment, and calls each module's `frontendModule` as `build` did. The options it computes replace the ones the build wrote, in the server and in every page it sends: a deployment that sets `DMS_API_PUBLIC_BASE_URL`, a Stripe key or any other variable an option reads needs no rebuild. Give the frontend the same values as the backend, for instance by referencing the backend's variables.

## The server's secrets

The server reads every secret from its environment, where the build left none:

| Variable | What it must equal | Unset |
| --- | --- | --- |
| `DMS_SESSION_SECRET` | 32 characters or more, the same across restarts | `start` refuses to run |
| `DMS_HTML_RENDER_SECRET` | The backend's `htmlRender.serviceSecret` | E-mail renders are refused |
| `DMS_OAUTH_RELAY_SECRET` | The backend's OAuth relay secret, an HMAC-SHA256 of its JWT secret | OAuth sign-in is refused by the backend |
| `DMS_PRIVATE_OPTIONS` | Any other private option a module publishes, as JSON by module id: `{"acme__shop-frontend-vue":{"apiKey":"…"}}` | The module's server routes get an empty value |

The module ids are the keys of `generated-server-options.json` in the workspace, which lists every private option with its value emptied. `start` warns, before the server starts, about each one it runs without, naming the module and the option.

## A build shipped with its project

`--workspace <dir>` serves the build that `ajs dms build --workspace <dir>` made, wherever it is, for instance in a container image. `start` writes nothing into it, so the directory and the image can be read-only.

```bash [Terminal]
ajs dms start --workspace .dms-frontend -p 3000
```

## Telling the backend what it serves

Once the server is ready, `start` posts to the backend's `POST /dms/frontend/ready`, with `DMS_BOOTSTRAP_SECRET`, the name and version of each module it serves and its own version. The backend compares them with the versions it runs and logs a warning naming each module that differs: deploy the frontend and the backend from the same commit. The server never waits for the answer. A backend that is asleep, starting (a `5xx`) or out of reach gets the report again in the background, after 2 seconds and then twice as long each time up to a minute, until it first answers; any other answer, such as a refused credential, ends it.

## Defaults that differ from dev

| | `dev` | `start` |
| --- | --- | --- |
| Address it binds to (`HOST`) | `127.0.0.1` | `0.0.0.0` |
| `Secure` cookies (`DMS_COOKIE_SECURE`) | Off | On |
| Builds of Vue and its libraries (`NODE_ENV`) | Development | Production |
| Session secret (`DMS_SESSION_SECRET`) | Generated when unset | Required, the same across restarts |
| Busy port | Moves to the next free one | Stops |

`start` runs the server with `NODE_ENV=production` unless the environment, or the project's `.env`, sets another value. Vue, its server renderer and vue-i18n read it when the server loads them: under any other value, pages render with their development builds, slower and printing `[Vue warn]` messages, and `start` warns before the server starts:

```text
▲ NODE_ENV is development: the server renders with the development builds of Vue and its libraries
  → Unset it for start, or set it to production
```

Production cookies are `Secure`, so a browser only sends them over HTTPS. Put `start` behind a TLS-terminating reverse proxy, or set `DMS_COOKIE_SECURE=false` for a plain-HTTP test.

## Errors

```text
$ ajs dms start -b https://dms.example.com
✖ No production build to serve
  ./.dms-frontend has no built server or client.
  → Build it first: ajs dms build
```

```text
$ ajs dms start -b http://localhost:5050 -p 3007
ajs dms start  http://localhost:5050 · production · built 3 min ago
✖ Port 3007 is already in use
  → Stop the process listening on it, or pass another port: -p <port>
```

Ctrl+C stops the server and exits with code `130`:

```text
■ Stopped the production server · ran 27.4s
```
