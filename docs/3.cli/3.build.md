# build

`ajs dms build` builds the production frontend of an AntelopeJS project: the client bundle, its compressed copies, the server-rendering bundle, the e-mail bundle and the bundle of the modules' server routes. It reads the project, not a backend.

```text
$ ajs dms build --help
Usage: ajs dms build [options]

Build the production frontend from the AntelopeJS project itself: its
antelope.config.ts, evaluated for the environment, and the frontend of each
installed module that declares one (dmsFrontend in its package.json). No backend
is asked. The build holds no secret, and start computes the modules' options
again from the deployment's variables.

Options:
  --project <dir>          The AntelopeJS project whose antelope.config.ts and
                           installed modules make the frontend (default: ".")
  -e, --env <environment>  The AntelopeJS environment whose configuration
                           applies, as ajs project start -e (default:
                           "production", env: ANTELOPEJS_LAUNCH_ENV)
  --workspace <dir>        Build into this directory instead of
                           <project>/.dms-frontend (env: DMS_WORKSPACE_DIR)
  -f, --force              Reinstall the workspace dependencies
  -h, --help               Show help for a command
```

## What the build reads

The backend and the frontend are built from the same repository, so the frontend computes everything itself:

1. **The modules and their configuration**: `antelope.config.ts`, evaluated by AntelopeJS's own config loader with the rules `ajs project start -e <env>` applies: the environment's section, the modules' JSON files and `envOverrides`. `${@api.API_PUBLIC_BASE_URL}` and the other api variables resolve from the api module's configuration.
2. **Each module's frontend**: the module's installed package, `node_modules/<package>` (or AntelopeJS's module cache, or the local source path), and the file it names as `dmsFrontend` in its `package.json`. That file exports `frontendModule(config, { dev })`, the same pure function the module's backend passes to `AddFrontendModule`: it returns the frontend source directory, its options and the backend routes it declares.
3. **The modules' versions**: from each package, locked by the project's lockfile.

Nothing goes over the network but the workspace's own `pnpm install`. A module whose package ships `frontend-vue/` without a `dmsFrontend` declaration is left out, with a warning; so is a configured module that is not installed (run `ajs project build` first).

The build keeps no secret. Private options are written with every value emptied, and `build` reads neither `DMS_SESSION_SECRET` nor the backend's secrets: [`start`](/docs/frontend/cli/start) reads them from its environment, and computes the public options again from the deployment's variables.

## A build

```text
$ ajs dms build
ajs dms build  . · production
✔ Workspace generated 2.1s
✔ Installed 812 packages 41.0s
ℹ Building for production
  Workspace  ./.dms-frontend
✔ Built the client bundle 1m 38s
✔ Compressed the client assets 32.2s
✔ Built the SSR bundle 1m 35s
✔ Built the e-mail bundle 3.6s
✔ Built the server modules 2.8s
▲ 1 Vite warning
  → Run with --verbose to list them

Built the production frontend → ./.dms-frontend/dist · 4m 41s

Next steps
  ajs dms start -b <backend>  from the project, with DMS_SESSION_SECRET, the server's secrets and the deployment's variables in its environment
```

The steps write into the workspace's `dist/` directory:

| Step | Output |
| --- | --- |
| Client bundle | `dist/client`, the browser application |
| Compressed assets | Pre-compressed copies of the client assets, which the server sends to browsers that accept them |
| SSR bundle | `dist/ssr`, the server renderer |
| E-mail bundle | `dist/server`, the e-mail renderer and its translation catalogs under `dist/server/locales/` |
| Server modules | `dist/server-modules`, the modules' `dms.server.ts` and what they import |

A step that fails stops the build, prints the error Vite reported, or the last lines of the step's output, and points at the file in the module rather than its copy in the workspace. `--verbose` streams every line of every step.

The workspace's files are readable by other users, since they hold no secret: an image is often built as one user and served as another.

## The client entry

Every page loads the client entry, and what it imports statically, before it runs anything. A module's `dms.frontend.ts`, its plugins and whatever they import are part of it, so their weight is paid on every page of the application, the sign-in page included. Once the build succeeded, it reports what the entry weighs and how much of it each frontend module's sources make up, estimated from the bundle's own metadata at no build cost:

```text
ℹ Client entry 444 KB Brotli (1.8 MB), loaded first by every page
  shared  263 KB (1 MB)
  translations  95 KB (388 KB)
  @antelopejs/dms-frontend-vue  43 KB (175 KB)
  @acme/reports-frontend-vue  61 KB (250 KB)
  …
▲ @acme/reports-frontend-vue adds 61 KB Brotli to the client entry
  What a module's dms.frontend.ts and its plugins import is loaded by every page: render a component they only show on some pages by its registered name or with defineAsyncComponent
  The threshold is 50 KB (DMS_ENTRY_WEIGHT_WARNING, in KB; 0 turns the warning off)
```

`shared` is what no single module owns: the renderer's runtime, Vue, the UI and icon libraries and the bundler's own code. `translations` is the merged translation catalog, when it is part of the entry. Each chunk's bytes are shared out among the modules it holds in proportion to the code the bundler rendered for each before minification, and each module's Brotli size is its share of the entry's. Code shares are within a few percent; data that minification does not shrink, such as a translation catalog, comes out about a quarter lower than it is.

A module above `DMS_ENTRY_WEIGHT_WARNING` KB of Brotli (50 by default, a little above the DMS core module's own 43 KB) gets a warning; the build still succeeds. The usual cause is a plugin that imports a component only some pages show: render the component the module registers by its name, or wrap it in `defineAsyncComponent`, and its code loads with the pages that show it.

## Forcing a clean build

`build` reinstalls the workspace dependencies only when the modules' dependencies changed. `--force` reinstalls them. To start from an empty workspace, delete it first.
