`ajs dms build` builds the production frontend of an AntelopeJS project. That is the client bundle, its compressed copies, the server-rendering bundle, the e-mail bundle and the bundle of the modules' server routes. It reads the project, not a backend.

```text
$ ajs dms build --help
Usage: ajs dms build [options]

Build the production frontend from the AntelopeJS project itself: its
antelope.config.ts, evaluated for the environment, and the frontend of each
installed module that declares one (dmsFrontend in its package.json). No backend
is asked. The build holds no secret, and start computes the modules' options
again from the deployment's variables.

Options:
  --project <dir>          The AntelopeJS project whose antelope.config.ts and
                           installed modules make the frontend (default: ".")
  -e, --env <environment>  The AntelopeJS environment whose configuration
                           applies, as ajs project start -e (default:
                           "production", env: ANTELOPEJS_LAUNCH_ENV)
  --workspace <dir>        Build into this directory instead of
                           <project>/.dms-frontend (env: DMS_WORKSPACE_DIR)
  -f, --force              Reinstall the workspace dependencies
  -h, --help               Show help for a command
```

## What the build reads

The backend and the frontend are built from the same repository, so the frontend computes everything itself. It reads three things.

1. **The modules and their configuration.** AntelopeJS's own config loader evaluates `antelope.config.ts` with the rules `ajs project start -e <env>` applies. Those rules cover the environment's section, the modules' JSON files and `envOverrides`. A `${@<module>.<VAR>}` reference resolves with the function its provider declares as `antelopeJs.configVarsFile` in its `package.json`. That function is the pure `configVars(config)` the provider's own `provide` publishes from, and the build calls it with the provider's configuration. For example, `${@api.API_PUBLIC_BASE_URL}` is the api module's `publicBaseUrl`, or its local origin when `publicBaseUrl` is unset. A provider that is not installed, or that declares no such file, leaves its references unresolved.
2. **Each module's frontend.** The build reads the module's installed package, `node_modules/<package>`, or AntelopeJS's module cache, or the local source path. In it, it reads the file the package names as `dmsFrontend` in its `package.json`. That file exports `frontendModule(config, { dev })`, the same pure function the module's backend passes to `AddFrontendModule`. It returns the frontend source directory, its options and the backend routes it declares.
3. **The modules' versions.** Each package gives its version, locked by the project's lockfile.

Nothing goes over the network except the workspace's own `pnpm install`. The build leaves out, with a warning, a module whose package ships `frontend-vue/` without a `dmsFrontend` declaration. It also leaves out a configured module that is not installed. Run `ajs project build` first to install it.

The build keeps no secret. It writes private options with every value emptied, and it reads neither `DMS_SESSION_SECRET` nor the backend's secrets. [`start`](/docs/frontend/cli/start) reads them from its environment, and computes the public options again from the deployment's variables.

## A build

```text
$ ajs dms build
ajs dms build  . · production
✔ Workspace generated 2.1s
✔ Installed 812 packages 41.0s
ℹ Building for production
  Workspace  ./.dms-frontend
✔ Built the client bundle 1m 38s
✔ Compressed the client assets 32.2s
✔ Built the SSR bundle 1m 35s
✔ Built the e-mail bundle 3.6s
✔ Built the server modules 2.8s
▲ 1 Vite warning
  → Run with --verbose to list them

Built the production frontend → ./.dms-frontend/dist · 4m 41s

Next steps
  ajs dms start -b <backend>  from the project, with DMS_SESSION_SECRET, the server's secrets and the deployment's variables in its environment
```

The steps write into the workspace's `dist/` directory:

| Step | Output |
| --- | --- |
| Client bundle | `dist/client`, the browser application |
| Compressed assets | Pre-compressed copies of the client assets, which the server sends to browsers that accept them |
| SSR bundle | `dist/ssr`, the server renderer |
| E-mail bundle | `dist/server`, the e-mail renderer and its translation catalogs under `dist/server/locales/` |
| Server modules | `dist/server-modules`, the modules' `dms.server.ts` and what they import |

A step that fails stops the build, prints the error Vite reported, or the last lines of the step's output, and points at the file in the module rather than its copy in the workspace. `--verbose` streams every line of every step.

Other users can read the workspace's files, since they hold no secret. A container image is often built as one user and served as another.

## The client entry

Every page loads the client entry, and what it imports statically, before it runs anything. A module's `dms.frontend.ts`, its plugins and whatever they import are part of it, so every page of the application pays their weight, the sign-in page included. Once the build succeeds, it reports what the entry weighs and how much of it each frontend module's sources make up. It estimates the shares from the bundle's own metadata, at no build cost:

```text
ℹ Client entry 349 KB Brotli (1.4 MB), loaded first by every page
  shared  263 KB (1 MB)
  @antelopejs/dms-frontend-vue  43 KB (175 KB)
  @acme/reports-frontend-vue  61 KB (250 KB)
  …
▲ @acme/reports-frontend-vue adds 61 KB Brotli to the client entry
  What a module's dms.frontend.ts and its plugins import is loaded by every page: render a component they only show on some pages by its registered name or with defineAsyncComponent
  The threshold is 50 KB (DMS_ENTRY_WEIGHT_WARNING, in KB; 0 turns the warning off)
```

`shared` is what no single module owns. It holds the renderer's runtime, Vue, the UI and icon libraries and the bundler's own code. `translations` is the merged translation catalog, and it appears only when a module imports it statically. Otherwise the application loads each language's catalog on demand, from a file of its own. The report therefore leaves out the catalog the server preloads next to the entry for the page's language, although every page downloads it.

The report splits each chunk's bytes among the modules it holds, in proportion to the code the bundler rendered for each before minification. Each module's Brotli size is its share of the entry's. Code shares are within a few percent. Data that minification does not shrink, such as a translation catalog, comes out about a quarter lower than it is.

A module above `DMS_ENTRY_WEIGHT_WARNING` KB of Brotli gets a warning, and the build still succeeds. The default is 50, a little above the DMS core module's own 43 KB. The usual cause is a plugin that imports a component only some pages show. Render the component the module registers by its name, or wrap it in `defineAsyncComponent`, and its code loads with the pages that show it.

## Forcing a clean build

`build` reinstalls the workspace dependencies only when the modules' dependencies changed. `--force` reinstalls them. To start from an empty workspace, delete it first.
