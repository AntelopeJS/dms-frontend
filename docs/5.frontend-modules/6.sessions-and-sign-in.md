The frontend server keeps the session in a sealed, `HttpOnly` cookie and holds the access and refresh tokens on the server. The renderer itself serves no session, sign-in, OAuth or e-mail render route. Those routes belong to the DMS, which declares them in its own `dms.server.ts`. Without a module that registers auth hooks, pages carry no `user` and `session`, and a refused session is not renewed.

The screens a user sees, the sign-in form and the Security page, are covered in the illustrated [built-in authentication guide](/docs/auth-and-tenancy/authentication). This page covers the server hooks behind those screens. Registering a hook does not create a sign-in UI.

## Auth hooks

The server runs some session logic outside any route. It renews a session the backend refused on a page visit, builds the `user` and `session` page props, and sends a signed-out visit to sign in. The module that owns sign-in provides that logic:

```ts fragment [dms.server.ts]
server.registerAuth({
  signInPath: "/auth",
  signInExempt: ["/auth/**", "/onboarding"],
  refreshSession: renewSession, // (event, session) => the new session, or undefined
  publicSession: (session) => ({
    user: session.user,
    session: { accountId: session.accountId, activeTenantId: session.activeTenantId },
  }),
});
```

- **`refreshSession`** runs once when the backend answers `401` to a signed-in page visit. The server then retries the visit with the session the hook wrote through `event.session.write`.
- **`publicSession`** returns the page props of a signed-in session. The server adds `session.updatedAt`, the time of the last write, and `event.session.view()` returns the same props to a route.
- **`signInExempt`** patterns are `/x`, `/x/*` (one segment below) or `/x/**` (the page and everything below). When the option is left out, the patterns are `<signInPath>/**` and `/onboarding`, so a custom `signInPath` is exempt without more configuration.
- **`signInPath`** is where a signed-out visit to a private page goes, with `?redirect=`. It is `/auth` by default.

The highest-priority module that registers auth hooks provides all of them. The server reports and ignores the hooks of any other module.

::note
The DMS refreshes a token once per frontend process, for every request that needs it at the same time. A deployment scaled out to several processes uses sticky routing, so that a browser always reaches the same process. See [Production](/docs/frontend/deployment/production#scaling-out).
::

## Interface language

The interface language follows the session (`useDmsUserSession().user.language`), not the props of the page on screen. The first render takes the language from the session the page arrived with. The language changes when the session's language changes, after `useDmsUserSession().fetch()` or after a visit that brings a newer session.

- A page that Inertia restores from history, or serves from its prefetch cache, carries the session it was fetched with. If that page carries an older `session.updatedAt` for the same account, it updates neither the session nor the language.
- A session without a language, such as a signed-out one, keeps the language on screen. `$i18n.setLocale()` still switches the language at any time.
- The `dms_locale` cookie remembers the language chosen in the application, for one year, with `SameSite=Lax`. A page without a signed-in user's language, such as a public sign-in page, first renders in that language. A visitor's choice survives a reload, and a signed-in user's own language comes first.
- The CLI merges the `i18n/locales/*.json` files of the modules into one catalog per language, each in its own file outside the client entry. A language's catalog already holds the English message of every key it does not translate. The exception is the messages the renderer translates itself (`error.network.*`). A page therefore loads only its language's catalog, which the server preloads next to the entry.
- `te()` reads only the current language's catalog, so it also answers `true` for a key that only English translates.

## Opening a session from a module flow

`/auth/login`, `/auth/register` and `/auth/verify-2fa` are not the only ways a visitor becomes authenticated. A module can own a flow that ends with an authenticated user and needs the session opened at its end. A self-service registration that completes after payment is one case, and an invitation being redeemed is another. `POST /auth/establish` is the generic form of those routes.

The browser names a backend endpoint and the payload to send it. `$fetch` is an auto-import of the renderer, available in a module's source files without an import (see [Data loading](/docs/frontend/rendering/data-loading)). The `declare` line only gives this example the type that the renderer exports:

```ts
declare const $fetch: typeof import("@antelopejs/dms-frontend/templates/vue/frontend-module").$fetch;

await $fetch("/auth/establish", {
  method: "POST",
  body: {
    endpoint: "/api/saas/register/finalize",
    payload: { /* whatever that backend route expects */ },
  },
});
```

The frontend server calls that endpoint itself, server to server, the same way it calls the backend's login route. It writes the session from the token pair the backend answers with. The browser never sends or receives a token. It gets back the same `{ user, account }` body that the login route returns, and the two-factor and tenant-assignment outcomes work the same way as for a login.

Because the route turns a backend endpoint into a login, it calls only the endpoints declared for it. A backend module declares its own when it registers its frontend:

```ts [src/index.ts]
import path from "node:path";
import { AddFrontendModule } from "@antelopejs/interface-dms/page";

await AddFrontendModule({
  name: "@antelopejs/dms-saas-frontend-vue",
  sourcePath: path.join(__dirname, "../frontend-vue"),
  renderer: { name: "vue", version: "3" },
  authEstablishEndpoints: ["/api/saas/register/finalize"],
});
```

The DMS gathers the declared endpoints into the manifest, and `dev` and `build` write them into the workspace. `DMS_AUTH_ESTABLISH_ENDPOINTS` adds endpoints that no module declares, comma-separated. The allow-list is the union of both.

Each entry is matched exactly against absolute `/api/` paths, with no prefix match, no query string and no traversal. An undeclared endpoint gets a `403` and is never called. The route accepts `POST` only and requires the frontend's own origin, like every other auth action.
