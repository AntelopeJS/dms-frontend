# Auto-imports

Nothing a module ships is auto-imported unless the module declares it, in an optional `dms.frontend.build.ts` next to its `dms.frontend.ts`:

```ts [dms.frontend.build.ts]
import { defineDmsFrontendBuild } from "#dms/frontend-build";

export default defineDmsFrontendBuild((build) => {
  build.registerAutoImports([
    "layers/*/app/composables",
    "layers/*/app/utils",
    "layers/*/app/types",
  ]);
});
```

Each entry is a directory relative to the module root, glob patterns allowed. Every export of the files under it becomes available to the whole application without an import, in scripts and templates. A module without the file has nothing auto-imported.

## Private code stays private

`app/build/` holds a module's private code and is never auto-imported. A broader entry leaves it out, and an entry that names it, or a directory outside the module, is ignored with a warning when Vite starts. The module's own files import that code by path.

## Vite plugins

`registerVitePlugins` adds Vite plugins to the application's build, in the same file. A module can use it to enforce its import boundaries in production builds, with an `enforce: "pre"` plugin whose `resolveId` or `load` hook fails on a forbidden module id.

```ts fragment [dms.frontend.build.ts]
import { defineDmsFrontendBuild } from "#dms/frontend-build";
import { boundaryPlugin } from "./build/boundary-plugin";

export default defineDmsFrontendBuild((build) => {
  build.registerVitePlugins(() => [boundaryPlugin()]);
});
```

The function you pass runs in the build process each time Vite loads its configuration, and returns real Vite plugin objects: an array, each with a `name`, or nothing. As in a Vite configuration, `false`, `null` and `undefined` entries are skipped and nested arrays are flattened. The function is synchronous: Vite builds its configuration synchronously, so a Promise is refused. Create the plugins in it, and let their own hooks be async. The plugins run under `ajs dms dev`, `ajs dms build` and the preview, after the renderer's own plugins, in module order and then in the order of the calls. Vite orders plugins by their `enforce` first: the core resolver answers a relative or aliased import before a plugin without `enforce` sees it, so a plugin that must see every id sets `enforce: "pre"`. Use a plugin's `apply` to limit one to a command.

A value that is not an array of plugin objects fails Vite with a message that names the module. So does an error thrown by the function or by any hook of the plugins, including the function `configureServer` returns, and whether the plugin is an object or a class instance: the message starts with `Frontend module <name>:`.

## Where it runs

The file runs in Node.js when Vite starts, under `ajs dms dev` and `ajs dms build`, not in the application. It may import `#dms/frontend-build` and Node.js built-ins, never the application's code. Vite restarts when the file changes.

::note
Up to 0.3, every module's `app/composables`, `app/types`, `app/utils`, `app/build/composables` and `app/build/types` were auto-imported. A module that relies on auto-imports declares its public directories here, and imports its `app/build/` code by path.
::
