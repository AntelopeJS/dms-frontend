# Routing and the backend proxy

The frontend server answers each path with one owner, whoever asks and whatever the method. It looks for the owner in this order.

## Who answers a path

::steps
### The renderer

Its icon endpoint (`/api/_dms/icons`), Vite's URLs, the built assets, and any file it has: a development source, a built asset, a module's `public/` file.

In production, a path with a segment starting with a dot is never a built asset. Vite's build metadata under `dist/client/.vite/` stays private, including its compressed copies. A leading `/.well-known/` directory is the exception: its public files remain served.

### The module routes

The routes of the modules' `dms.server.ts`, for every method. A method the module does not declare on its path answers `405`, and a `HEAD` reaches the `GET` route. See [Server routes](/docs/frontend/frontend-modules/server-routes).

### The backend proxies

The prefixes the modules declare. The renderer proxies no path on its own: the DMS declares `/api/**` and `/dms/**` in its `dms.server.ts`.

### The pages

Everything else is a page. A method other than `GET` and `HEAD` there is a `404`. A backend route outside every declared prefix, such as a page's `<page>/pagelayout`, is never reached from the browser.
::

The server lists the result when it starts:

```text
Routing: renderer files, then 21 module routes, then the backend proxies below, then the pages
  /file-storage/upload/**  -> backend (none), declared by antelopejs__dms-frontend-vue
  /file-storage/files/**   -> backend (none), declared by antelopejs__dms-frontend-vue
  /api/**                  -> backend (session), declared by antelopejs__dms-frontend-vue
  /dms/**                  -> backend (session), declared by antelopejs__dms-frontend-vue
  /ai/**                   -> backend (session), declared by @antelopejs/dms-ai-frontend-vue
  /i18n/**                 -> backend (none), declared by @antelopejs/dms-lang-frontend-vue
  /media/**                -> backend (session), declared by @antelopejs/dms-media-frontend-vue
```

In development, every answer names its owner in an `x-dms-route-owner` header: `renderer`, `module:<id>`, `backend:<pattern>`, `page` or `not-found`.

## Declaring a backend prefix

::tabs
:::tabs-item{label="Frontend module" icon="i-lucide-monitor"}
In `dms.server.ts`:

```ts fragment [dms.server.ts]
server.registerBackendProxy("/api/**"); // auth: "session", the default
server.registerBackendProxy("/media/**", { auth: "none" });
server.registerBackendProxy("/uploads/**", {
  auth: "none",
  maxBodyBytes: 100 * 1024 * 1024,
});
```
:::

:::tabs-item{label="Backend module" icon="i-lucide-server"}
In the manifest, next to its `publicEndpoints`:

```ts fragment [src/index.ts]
await AddFrontendModule({
  // …
  backendProxies: [{ path: "/webhooks/acme/**", auth: "none" }],
});
```
:::

:::tabs-item{label="Operator" icon="i-lucide-terminal"}
`DMS_BACKEND_PROXIES` adds entries of the manifest's shape, as a JSON array:

```bash [.env]
DMS_BACKEND_PROXIES=[{"path":"/webhooks/acme/**","auth":"none"}]
```
:::
::

- **`auth: "session"`** adds the session's access token to the request (`Authorization: Bearer`), server-side: the token never reaches the browser, which only holds the sealed, `HttpOnly` session cookie. A request with a state-changing method must carry the frontend's own `Origin`, except on a [public endpoint](/docs/frontend/deployment/public-endpoints).
- **`auth: "none"`** never sends the session, so it needs no `Origin`: for media, or a webhook that authenticates its caller itself.
- **`maxBodyBytes`** caps the request body the proxy streams to the backend, in bytes. A larger declared `Content-Length` gets a `413` before any byte is passed on; a chunked body is cut off with a `413` as soon as it goes over. The server then reads and drops what the client is still sending, for 5 seconds at most, before it closes the connection, so that the client receives the `413` rather than a reset connection. No cap by default: the backend applies its own.

A pattern is `/x`, `/x/*` (one segment below) or `/x/**` (the path and everything below), its first segment literal, outside the renderer's own paths. Of two patterns covering a path, the more specific wins. For one pattern, the highest-priority frontend module's declaration wins, then the manifest's, with a warning.

::warning
The manifest's `backendProxies` reach the frontend only when it is fetched with the bootstrap credential. A build made without `DMS_BOOTSTRAP_SECRET` serves only the prefixes the modules' `dms.server.ts` declare.
::

## What the proxy sends

Every proxied request relays:

- the client headers a backend route reads about the browser: `User-Agent`, `X-Content-Language` (the interface language), `X-Realtime-Session` and `X-Realtime-Connection` (a tab's realtime session and the browser connection its tabs share). Module routes' `event.backend()` sends the same ones;
- `If-Match`, so a backend route can refuse a write made from a stale copy (`412` or `409`);
- the client's `Origin` and `Referer` as received, so a public route can check where a beacon comes from;
- `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host`, set by the proxy itself so a route can limit each client. The client's own `X-Forwarded-For` is extended with the socket's address only behind `DMS_TRUSTED_PROXY_HOPS` trusted proxies, and replaced by it otherwise.

The proxy matches the request's normalized path, the one it sends the backend, so `..`, `%2e%2e` or `\` cannot reach another route through a declared prefix.

The proxy never relays the client's `Cookie` or `Authorization`: the backend gets the session's token only through `auth: "session"`. The server writes no access log, so a token in a query string, such as a signed file URL's, stays out of its output.

## Redirects

The proxy never follows a backend redirect: the browser does. A `301`, `302`, `303`, `307` or `308` reaches the browser with its status, its `Location` and the backend's own cookies, so a redirect to another site sends the browser there instead of serving that site's page, and its cookies, from the frontend's origin.

The proxy keeps paths as they are, so a `Location` on the backend's origin (`DMS_API_BASE_URL`) becomes the same path on the frontend's when the frontend server sends that path to the backend, that is when a backend proxy covers it and no renderer file or module route takes it first (see [Who answers a path](#who-answers-a-path)): `http://localhost:5010/api/files/1` reaches the browser as `/api/files/1`. A `Location` on a backend path the frontend does not proxy, a route outside every declared backend proxy (`http://localhost:5010/exports/report.pdf?token=…`), stays an absolute backend URL: the browser follows it to the backend, which must then be reachable from the browser on that origin. A relative `Location` is read against the backend URL and follows the same rule; one on another site is relayed unchanged. This applies to every backend proxy and public endpoint, in development and in production.

## Large transfers

The proxy streams the request body to the backend and the answer back to the client as they come, whatever their size: neither is held in memory. A transfer may last an hour: the server allows that long to receive a request, instead of Node's five minutes, and Node's own minute still bounds the headers. The backend's answer has no deadline once it starts, only five minutes between two parts.

The DMS declares the storage's signed URLs, `/file-storage/upload/**` (`PUT`, capped at 500 MiB) and `/file-storage/files/**` (`GET`, `HEAD`), with `auth: "none"`: the token in the URL authenticates them. A backend reachable only through the frontend still receives uploads and serves downloads when the storage's `baseUrl` is the frontend's public URL. Resource keys keep their encoded slashes (`%2F`): the storage checks every segment of a key itself.

## Response compression

The proxy asks the backend for an uncompressed answer. It compresses eligible text (JSON, text, XML and SVG) of at least 1 KiB, or of unknown length, using Brotli or gzip according to the client's `Accept-Encoding` qualities. Streaming compression delivers each part as the backend writes it. Eligible answers include `Vary: Accept-Encoding` even when the client receives identity bytes.

The proxy does not compress event streams, ranges, answers marked `no-transform`, or opaque encoded bodies. If the backend ignores the identity request, native fetch decodes supported encodings; the proxy removes the stale encoding and length before relaying or recompressing that body. A decoded encoded range returns `502` rather than forwarding byte offsets that no longer describe its body. HEAD and bodyless responses retain their representation metadata.

## Event streams

The proxy relays a long-lived answer, such as a `text/event-stream` feed, as the backend writes it, for as long as both sides keep it open. When either side stops, only that response ends:

- a client that leaves closes its backend request, and one that left while its request was being routed opens none;
- a backend stream that breaks (the backend restarts, the connection drops) ends the client's response, and the server keeps serving every other request.

Node's `fetch` ends a backend answer that sends nothing for 5 minutes (undici's `bodyTimeout`, 300 s between two chunks). The proxy keeps that limit: it is what eventually frees a backend connection whose peer vanished without closing it. An event stream that must stay open through quiet periods sends a comment line (`: keepalive`) more often than that, as the DMS realtime stream does every 20 s. One that does not is ended after 5 quiet minutes and the browser's `EventSource` reconnects by itself, after the `retry` delay the stream set.
