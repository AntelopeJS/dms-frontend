# Production

A production frontend is two commands run from the AntelopeJS project the backend is built from: `ajs dms build` builds it from the project's configuration and installed modules, without the backend, and `ajs dms start` serves it. The backend itself is deployed separately; see [Deployment](/docs/building/deployment) in the DMS guide.

## Deploy

::steps
### Set the configuration

Put the values in the environment of the machine or container, or in the `.env` of the directory you run the commands from:

```bash [.env]
DMS_API_BASE_URL=https://api.example.com
DMS_API_PUBLIC_BASE_URL=https://api.example.com
DMS_CLIENT_BASE_URL=https://dms.example.com
DMS_BOOTSTRAP_SECRET=the backend's frontend.bootstrapSecret
DMS_SESSION_SECRET=output of openssl rand -hex 32
DMS_HTML_RENDER_SECRET=the backend's htmlRender.serviceSecret
DMS_OAUTH_RELAY_SECRET=the backend's OAuth relay secret
```

`build` reads none of them. `start` evaluates the project's configuration with them, as the backend does, so the variables its `envOverrides` read must have the backend's values; `DMS_BOOTSTRAP_SECRET` lets it tell the backend which module versions it serves. `DMS_SESSION_SECRET` must stay the same across starts and restarts. See [Configuration](/docs/frontend/configuration#the-secrets) and [the server's secrets](/docs/frontend/cli/start#the-servers-secrets).

### Build

```bash [Terminal]
ajs project build -e production
ajs dms build
```

`ajs project build` installs the configured modules, whose frontends `ajs dms build` reads. The build takes a few minutes: four minutes for the twelve modules of the DMS demo template. It ends with where it wrote the build and the command to run next. See [`ajs dms build`](/docs/frontend/cli/build).

### Start

```bash [Terminal]
ajs dms start -p 3001
```

The server binds to `0.0.0.0` and sets `Secure` cookies. Run it under a process manager that restarts it, and stop it with `SIGINT` or `SIGTERM`. See [`ajs dms start`](/docs/frontend/cli/start).

### Put it behind HTTPS

Terminate TLS in a reverse proxy in front of the server, and tell the server which header the platform writes the client's address in with `DMS_CLIENT_IP_HEADER`, or how many proxies it can trust with `DMS_TRUSTED_PROXY_HOPS`, so that it reads the client's address and country from them. See [Security](/docs/frontend/deployment/security#behind-a-reverse-proxy).

Raise the reverse proxy's own limits for the storage's signed URLs, `/file-storage/upload/**` and `/file-storage/files/**`: a body of 500 MiB and transfers of up to an hour, which the server itself allows. See [Large transfers](/docs/frontend/deployment/routing-and-proxy#large-transfers).

On AntelopeJS Cloud, Cloudflare sits in front of the frontend and caps every request body at 100 MB at the edge, below the server's 500 MiB cap: a larger upload gets Cloudflare's own `413` and never reaches the frontend server. The cap cannot be raised from the app.

`start` serves HTTP/1.1. In production, use a reverse proxy that speaks HTTP/2 or HTTP/3 to browsers, such as nginx, Caddy or a CDN. Pages load multiple JavaScript chunks: multiplexing those requests avoids the browser's per-origin HTTP/1.1 connection limit.
::

## Where the build lives

`build` writes into `<project>/.dms-frontend`, and `start` serves from there; `--workspace <dir>` moves it, for both.

## In a container image

An image build has neither the backend nor the secrets, and the container often runs as another user, on a read-only file system. The image holds the project, so it builds the frontend from it:

::steps
### Build in the image

From the project root, after installing its dependencies:

```bash [Terminal]
ajs project build -e production
ajs dms build
```

No backend, no credential, no variable: the build only reads the project and installs the workspace's dependencies.

### Start the container

```bash [Terminal]
ajs dms start -p "$PORT"
```

with `DMS_API_BASE_URL`, `DMS_SESSION_SECRET`, `DMS_HTML_RENDER_SECRET` and `DMS_OAUTH_RELAY_SECRET` (and `DMS_PRIVATE_OPTIONS` when a module publishes other private options) in the container's environment, the variables the project's `envOverrides` read, and `DMS_BOOTSTRAP_SECRET` so that `start` reports its module versions. `start` writes nothing into the workspace.
::

The served output is the workspace's `dist/` directory plus `server.mjs`, `server/` and the workspace's `node_modules`, and the project, which `start` reads its configuration from. Deploy the whole `dist/server` directory: it holds the e-mail renderer and the translation catalogs it loads at render time.

## Rebuilding

Rebuild, and redeploy the backend from the same commit, after installing, removing or upgrading a module that ships a frontend, and after upgrading `@antelopejs/dms-frontend`. A change of variable only needs a restart.

Once ready, `start` posts the name and version of each frontend module the build serves, and the renderer version, to `POST /dms/frontend/ready`. The backend warns when its own module versions differ, and the DMS Modules page reads the report. In development, the renderer reports again after each manifest read that finds the module set unchanged, so a restarted backend receives it within the three-second polling interval.

## Caching in front of the server

Page documents and Inertia answers are `private, no-cache` by default, since they carry the visitor's session. A module can make an anonymous page cacheable by a shared cache or a CDN with a [route rule](/docs/frontend/frontend-modules/route-rules). Built assets are pre-compressed with Brotli and gzip, and the server sends the compressed copy to a browser that accepts it, with `Vary: Accept-Encoding`.

Built files carry their MIME type. Content-hashed files under `/assets/` use `public, max-age=31536000, immutable`. Other files, including a layer's `public/` files, use `no-cache`, an `ETag` and a `Last-Modified`: browsers revalidate them and receive `304` without a body while they remain unchanged. Import frequently used files such as fonts through CSS or code so Vite gives them content-hashed names under `/assets/`.

## Scaling out

Session refresh is single-flight within one frontend process: when a token expires, one request renews it and the others wait for it. A horizontally scaled deployment must use sticky routing, so that a browser always reaches the same process. The frontend server provides no distributed refresh guarantee.
